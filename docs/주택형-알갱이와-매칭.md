# 주택형 알갱이와 매칭

`26A`, `26형(고령자)`, `26`이 다 같은 집을 가리키는데 원천마다 다르게 부른다. 어느 것을 카탈로그에
두고 어느 것을 공고에 둘지, 둘을 무엇으로 잇는지 정한 기록이다. 2026-08-16 21:52 KST 전체 재적재 v4 DB 실측 기준
(단지 3,038 · 주택형 10,024 · 공고 52 · 공급행 273).

## 2. LH는 순수형과 대상형을 섞어 주지 않는다

`26A`와 `26A(청년)`이 같은 공고·같은 단지에 **둘 다 오는 경우는 0건**이다. 한 주택형을 공급대상으로
쪼개면 쪼갠 행만 주고, 안 쪼개면 이름만 준다.

현재 주택형 공급행은 252개다. 공급대상이 붙은 행과 순수 주택형명만 있는 행이 함께 있지만,
공급대상 표기는 자유 텍스트라 단순 괄호 여부만으로 정확히 분류하지 않는다.

한 단지 안에서 두 형태가 보이는 건 4건인데, 열어 보면 **같은 주택형이 아니라 다른 주택형**이다.

```
부산정관 A4블록 :  16형 · 36형                          ← 대상 없음
                26형(고령자) · 26형(고령자,주거약자) · 26형(주거급여수급자)

남양주진접2    :  55A · 55B                            ← 대상 없음
                55AS(주거약자)                          ← 이름이 AS 로 다르다

화성동탄2 A-6  :  23형 (140세대)
                23B형(주거약자) (76세대)                ← 이름이 23B형
```

**주거약자·고령자 배정분은 주택형명 자체가 갈린다.** `55A`↔`55AS`, `23형`↔`23B형`처럼. 그래서
괄호를 떼는 파싱만으로는 부족하고, `55AS`를 `55A`로 되돌리면 안 된다 — 별개 주택형이다.

## 4. 매칭 규칙

```
notice_supply.housing_complex_id   ← suppliedPnu + 공고 supplyTypeName, 후보 1건일 때만
notice_supply.unit_type_id         ← 위 단지의 UnitType 중
                                     ① 전용면적 ±0.05㎡ 후보가 1건이면 그걸로
                                     ② 여럿이면 전용면적이 정확히 같은 게 1건일 때 그걸로
                                     ③ 그래도 여럿이면 공급면적(전용+주거공용)이 맞는 게 1건일 때 그걸로
                                     ④ 아니면 unmatched_reason 만 남긴다
```

[NoticeSupplyCatalogLinker.java](../src/main/java/test/domain/ingest/NoticeSupplyCatalogLinker.java)

**이름은 매칭에 쓰지 않는다.** 면적 모호 29건에 규칙을 다 돌려본 결과다.

| 규칙 | 붙는 행 |
| --- | ---: |
| 이름 정규화 후 비교 (`26형(고령자)` → `26형` → `26`) | **0** |
| ② 전용면적 완전일치 | **21** |
| ③ 공급면적 | **8** |
| | **29 / 29** |

이름이 0인 이유는 두 가지다. 접미사가 어긋나고(`26형` vs `26`, `23B형` vs `23B`), 더 결정적으로
카탈로그가 두 면적을 **같은 이름으로** 부른다.

```
LH 공고      :  22A@22.18   22B@22.14
카탈로그     :  22 @22.14 | 22 @22.18      ← 둘 다 이름이 `22`
```

이름으로는 애초에 못 가른다. 면적이 유일하게 작동하는 신호다.

### ③ 공급면적이 필요한 이유

②로도 안 갈리는 8건이 있었다. 카탈로그에 **전용면적이 똑같고 주거공용만 다른** 주택형이 여럿인 단지다.

```
산남주공2단지  26.37㎡ + 12.17㎡ = 38.54   ← 공고 SPL_AR 38.54
산남주공2단지  26.37㎡ + 13.56㎡ = 39.93
```

이름은 둘 다 `26`, 전용면적은 둘 다 26.3700이라 앞의 두 규칙으로는 못 가른다. 15056765가 `DDO_AR`
(전용) 옆에 `SPL_AR`(공급)을 같이 주고 우리가 그걸 `notice_supply.supply_area`에 이미 저장하고
있어서, 그걸로 가른다. 8건 전부 유일하게 확정됐다.

```
현재 v4 DB
주택형 확정               224
면적 모호로 못 고름         0
```

남은 51건은 전부 앞 단계 손실이다(주소 24 · PNU 11 · LH 원천 16).

## 5. 이 규칙의 한계 — FK 가 "주택형"인지 "모집단"인지 흐리다

부산정관 A4블록 세 행을 보면 드러난다.

| `HTY_NNA` | `DDO_AR` | 금회 | 전체(`HSH_CNT`) |
| --- | --- | --- | --- |
| `26형(고령자)` | 26.7500 | 10 | **288** |
| `26형(고령자,주거약자)` | 26.7500 | 40 | **44** |
| `26형(주거급여수급자)` | 26.7500 | 30 | **288** |

카탈로그는 26.75㎡ 44세대 / 26.78㎡ 244세대. **44 + 244 = 288**이다.

주거약자용은 26.75㎡ 44세대에서만 뽑고, 나머지 둘은 26형 전체(두 면적 합)에서 뽑는다. 그런데
LH는 세 행 모두 `DDO_AR`을 26.7500으로 준다.

우리 규칙은 세 행을 전부 26.75㎡ 주택형에 붙인다. 주거약자 행은 정확하고, **나머지 둘은 모집단이
두 주택형에 걸쳐 있는데 하나에만 붙는다.**

- 붙이기 전보다 나쁘지는 않다 — 전에는 셋 다 미확정이었다.
- 대신 `unit_type_id`는 **"이 공급행이 말하는 주택형"**이지 **"이 공급행이 뽑는 모집단"**이 아니다.
- 그래서 `unit_type_id`로 세대수를 집계하면 안 된다. 현재 양쪽 전체 세대수가 모두 있는 106건 중 **53건이 어긋난다**.

FK를 더 많이 채워도 이 문제가 사라지지 않는다. 현재 비교 가능한 106건 중 53건(50%)이 어긋난다.
**매칭의 정확도 문제가 아니라 두 원천이 세는 대상이 다른 문제**다.

## 6. 세대수 네 개는 서로 다른 걸 센다

| 컬럼 | 무엇을 세나 | 원천 | 채움 |
| --- | --- | --- | --- |
| `housing_complex.unit_count` | 이 단지·공급유형의 전체 세대수 | 15110581 `hshldCo` | 100% |
| `unit_type.total_unit_count` | 이 **전용면적**의 단지 전체 세대수 | 15059475 `HSH_CNT` | **15%** |
| `notice_supply.unit_total_count` | 이 공급행이 뽑는 **모집단** 크기 | 15056765 `HSH_CNT` | 주택형 행 전부 |
| `notice_supply.unit_supply_count` | **금회 공급호수** | 15056765 `NOW_HSH_CNT` | 주택형 행 전부 |

**섞으면 안 되는 두 가지가 있다.**

`unit_total_count`는 주택형 단위 값을 **공급대상 행마다 복사해서** 싣는다. 합치면 안 된다.

```
대구연경 A3블록
  26A(고령자)        금회  3   전체 60
  26A(대학생, 청년)   금회 15   전체 60     ← 같은 60 이 반복된다
  26A(주거급여수급자)  금회  5   전체 60
```

`sum(unit_total_count)` 하면 26A가 180세대가 된다. 세대수를 세려면 `unit_supply_count`(금회)를
쓰거나, `unit_total_count`는 주택형별로 하나만 골라야 한다.

그리고 `unit_type.total_unit_count`(전용면적 단위)와 `notice_supply.unit_total_count`(모집단)는
**서로 채워 넣을 수 없다.**

```
26.53㎡  →  카탈로그 120  =  공고 26A 80 + 26B 40
26.91㎡  →  카탈로그 538  =  공고 26A 388 + 26A1 150
```

둘 다 각자 맞는 값이라, 한쪽을 다른 쪽에 넣으면 그냥 틀린 값이 된다.

`total_unit_count`가 15%인 것도 정상이다. 15059475가 국민·행복·영구 계열만 다뤄서 50년·10년·5년임대
1,933개는 0건이고, 단지명으로만 붙어 6,710행 중 1,481행만 확정된다.

```
LH   6,648 주택형  →  1,481 (22%)
비LH 3,376 주택형  →      0        ← SH 2,415 가 여기
```

SH·GH 주택형별 세대수를 주는 원천은 포털에 없다. 이 컬럼은 **LH 단지에만 차고, 채워지면 쓰고 없으면
없는 대로** 두는 컬럼이다. `null`이 정상값이고 `sum(total_unit_count)`는 전국 물량이 아니다.

## 7. 공급대상은 지금 분리하지 않는다

`26A(청년)`을 주택형 `26A` + 대상 `청년`으로 쪼개는 일이다. 설계 문서의 `ApplicationOption` 자리인데,
지금은 하지 않기로 한다. 이유 셋이다.

### ① 매칭이 좋아지지 않는다

이름을 분리해도 카탈로그 연결은 그대로다. 4장에서 본 대로 이름으로 풀리는 건 **0/29**다. 분리해서
얻는 건 매칭 개선이 아니라 화면 표시·필터링 편의뿐이다.

### ② 코드가 아니라 사람이 손으로 친 텍스트다

대상이 붙은 156행에 **서로 다른 표기가 45개** 있다. 그중 20개는 딱 한 번씩만 나온다.

| 같은 뜻인데 | 표기 |
| --- | --- |
| 고령자 + 주거약자 | `고령자-주거약자` · `고령자,주거약자` · `고령자주거약자` · `고령자주거약자형` · `고령자주거약자용` · `고령자 주거약자용` · `주거약자용고령자` · `고령자-주거취약` |
| 대학생 + 청년 | `대학생/청년` · `대학생,청년` · `대학생, 청년` · `대학/청년` · `대학생 및 청년` |
| 신혼부부 + 한부모 | `신혼부부·한부모가족` · `신혼부부,한부모` · `신혼부부,한부모가족` · `신혼부부/한부모가족` · `신혼부부/한부모가족 계층` |

구분자가 `/` `,` `-` `·`로 섞이고, 붙여 쓰기도 한다. `신혼부부,한부모가족,청년,대학생고령자`는
쉼표가 빠진 오타로 보이고, `청년, 신혼부부·한부모가족, 고령자주거약자外`처럼 `外`가 붙기도 한다.
`TA`라고만 온 행도 하나 있다.

토큰 사전을 만들면 **원천이 아니라 우리가 정의를 발명하는 일**이 된다. 다음 공고가 새로운 표기를
가져오면 조용히 빠질 수 있다.

### ③ 쪼개면 오히려 거짓말이 된다

`26형(고령자)`와 `26형(고령자,주거약자)`를 주택형 `26형`으로 묶으면 같은 주택형처럼 보이는데,
5장에서 본 대로 **모집단이 288세대와 44세대로 다르다.** 지금은 이름이 달라서 다른 행인 게 보이지만,
대상을 떼어내면 그 차이가 이름에서 사라진다.

### 그럼 언제, 어떻게

먼저 **무엇에 쓸 건지**가 정해져야 한다. 용도마다 필요한 게 다르다.

| 용도 | 필요한 것 | 지금 되나 |
| --- | --- | --- |
| "청년 20호" 화면 표시 | 원문 | ✅ `type_name` 에 이미 있다 |
| "청년 대상 공고만" 필터 | 토큰 포함 검색 | ⚠️ `type_name LIKE '%청년%'` 로 대략 된다 |
| "청년에게 몇 호 배정" 집계 | 정규화된 토큰 집합 | ❌ 45개 표기를 정리해야 한다 |

앞의 둘은 지금 데이터로 된다. 세 번째가 실제 요구사항이 되면 그때 45개 표기를 정리한 **매핑표를
코드가 아니라 데이터로** 둔다 — `MyHomeRegionCatalog` 의 CSV, `LhSupplyInfoTypeResolver` 의 표처럼.
새 표기가 오면 조용히 버리지 말고 로그로 남긴다.

컬럼을 추가한다면 `notice_supply.supply_target_text` 하나면 된다. 괄호 안 원문을 **복사**하는 것이지
쪼개는 게 아니라, 파싱이 틀려도 `type_name` 원문이 그대로 남는다. 다만 지금은 그 컬럼도 필요 없다 —
`type_name` 에 대해 `LIKE` 하는 것과 차이가 없다.

## 9. 아직 안 정한 것 — `notice_supply` 의 두 알갱이

한 테이블에 주택형 행 252개와 단지 행 21개가 같이 있고, 마이홈이 준 단지 단위 임대료가 주택형 행마다
복사돼 있다(전용면적 6종인데 보증금 1종). `공고 × 주택형` 임대료는 어느 원천도 주지 않는데 테이블
모양은 그걸 가진 것처럼 생겼다.

**8장을 확인하다 알게 된 것 하나가 이 문제를 더 나쁘게 만든다.** 15108420 공식 Swagger 에서
`rentGtn`·`enty`·`prtpay`·`surlus`·`mtRntchrg` 의 필드명이 각각 `최소_임대_보증금`·`최소_계약금`·
`최소_중도금`·`최소_잔금`·`최소_월_임대료`다.

즉 우리가 주택형 행마다 복사하고 있는 값은 **단지 대표값이 아니라 그 공급행에서 가장 싼 값**이다.
대구연경 A3블록이면 16.66㎡ 주택형의 보증금이 36.57㎡ 행에도 그대로 붙어 있다는 뜻이다.

정리할 때 선택지는 둘이다.

- 주택형 행에서 `deposit`·`monthly_rent` 를 비우고 `house_sn` 대표행에만 남긴다. 컬럼 이름도
  `min_deposit` 처럼 최솟값임이 드러나게 바꾼다.
- 주택형별 임대료가 정말 필요하면 `unit_type.base_deposit`(10,024/10,024)을 쓰되, 그건 카탈로그
  **현재 기준값**이지 공고 시점 값이 아니라는 걸 감수한다.
