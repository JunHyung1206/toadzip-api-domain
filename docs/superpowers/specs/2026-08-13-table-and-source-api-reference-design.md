# 테이블 설계 사전·원천 API 명세 문서 설계

## 1. 목적과 독자

이 프로젝트를 처음 보는 개발자가 코드를 먼저 읽지 않아도 다음 질문에 답할 수 있는 문서 두 개를 만든다.

- 데이터가 왜 17개 테이블로 나뉘었는가
- 각 테이블의 행과 컬럼은 무엇을 뜻하는가
- 외부 원천 API에서 무엇을 어떤 요청으로 받아오는가
- 응답의 각 필드가 어느 테이블·컬럼에 저장되는가
- 어떤 원천과 필드는 사용하지 않으며 그 이유는 무엇인가

문서는 온보딩 설명서와 상세 레퍼런스의 역할을 함께 수행한다. 기존 `도메인-설계.md`와 `원천-API-데이터-사전.md`는 보존하고, 새 문서는 독립적으로 읽히게 작성한다.

## 2. 산출물

### `docs/테이블-설계-사전.md`

“왜 이 데이터 모델인가”에 답한다.

1. 문서 범위와 읽는 순서
2. 전체 ER 구조
3. 데이터의 네 층
   - 최신 주택 카탈로그
   - 공고 버전 이력
   - LH 보충 원천
   - 재계산 가능한 파생 매칭
4. 17개 테이블 관계 요약
5. 17개 테이블 상세 사전
6. 값 객체가 실제 컬럼으로 펼쳐지는 방식
7. enum과 상태값
8. 주요 조회 경로
9. 현재 적재 건수와 해석 시 주의점

각 테이블은 같은 형식을 반복한다.

- 행 하나의 의미
- 테이블이 필요한 이유
- 부모·자식 관계
- 생성·갱신·재계산 시점
- PK·FK·유니크 제약과 그 이유
- 전체 컬럼 표: DB 컬럼, Java 속성, 타입, NULL 허용, 의미, 값의 출처
- 설계상 주의점

`Address`, `CatalogDetails`, `BaseRentTerms`, `SuppliedHousing`, `RentTerms`, `NoticeHousingLhMatchEvidence`처럼 별도 테이블이 아닌 값 객체도 실제 DB 컬럼 기준으로 설명한다.

### `docs/원천-API-명세.md`

“외부에서 무엇을 어떻게 받아오는가”에 답한다.

1. 실제 사용하는 원천 API 네 개 요약
2. 공통 인증·호출·정상/오류 응답 처리
3. 15110581 마이홈 공공임대주택 단지정보
4. 15108420 마이홈 공공주택 모집공고
5. 15057999 LH 분양임대공고별 상세정보
6. 15056765 LH 분양임대공고별 공급정보
7. 원천 간 키 연결 지도
8. 적재 순서와 재호출 정책
9. 오류·자료 없음·부분 데이터 처리
10. 저장하지 않는 필드와 이유
11. 검토했지만 사용하지 않는 원천
12. 실제 적재 범위와 확인된 한계

각 API는 같은 형식을 반복한다.

- 원천이 답하는 질문
- 응답 한 행 또는 데이터셋의 알갱이
- HTTP 메서드와 엔드포인트
- 전체 요청 파라미터와 값의 출처
- 요청 예시
- 응답 봉투와 실제 형태를 축약한 JSON 예시
- 전체 응답 필드 표: 원천 필드, 타입, 의미, 예시, 저장 위치, 처리 방식
- 필터링·검증 규칙
- 다른 API와 이어지는 키

LH 상세 API 한 개가 `dsEtcInfo`, `dsSplScdl`, `dsCtrtPlc`, `dsSbd`, `dsAhflInfo`, `dsSbdAhfl` 등 여러 데이터셋을 반환한다. 이 데이터셋들을 각각 독립된 응답 단위로 설명해 “API 수보다 정보 종류가 많다”는 점이 드러나게 한다.

## 3. 원천 범위

자동 적재 코드가 호출하는 원천은 다음 네 개다.

| 데이터 ID | 역할 |
| --- | --- |
| 15110581 | 단지·공급유형·주택형 카탈로그 |
| 15108420 | 임대 모집공고·정정 체인·대상 주택·공고 임대조건 |
| 15057999 | LH 일정·접수처·단지 상세·첨부·정정사유 |
| 15056765 | LH 단지·주택형별 이번 회차 공급 세대수 |

다음 원천은 빠뜨린 대상이 아니라 검토 후 제외한 대상이다. 새 문서에 제외 이유를 기록한다.

| 대상 | 제외 이유 |
| --- | --- |
| 15058476 LH 공공임대주택 단지 기본정보 | 15110581로 대체된 구버전 |
| 15059475 LH 임대주택 단지별 조건 | 단지 ID·주소·PNU가 없어 안전하게 연결할 키가 없음 |
| 15058530 LH 분양임대공고문 | 정정 체인·PNU·임대조건이 없고 현재 원천을 대체하지 못함 |
| 15108420 분양공고 엔드포인트 | 프로젝트 경계가 건설임대이고 임대 카탈로그와 의미가 다름 |

개발용 `/admin/ingest/probe`는 임의 경로를 수동 호출할 수 있지만 자동 적재 원천으로 세지 않는다.

## 4. 문서 간 책임과 연결

- 테이블 문서는 저장 모델과 설계 판단을 기준으로 구성한다.
- API 문서는 외부 계약과 적재 변환을 기준으로 구성한다.
- 같은 내용을 길게 복제하지 않고 필요한 곳에 상호 링크를 둔다.
- API 문서의 저장 위치는 `테이블.컬럼`으로 명시한다.
- 테이블 문서의 값 출처는 API ID와 원천 필드명으로 명시한다.
- 원천 사실 테이블과 파생 매칭 테이블을 표현상 명확히 구분한다.

## 5. 사실 확인 기준

문서 내용은 다음 세 가지를 교차 확인한다.

1. JPA 엔티티와 `@Embeddable` 값 객체
2. 적재 서비스·원천 DTO·요청 DTO
3. 현재 H2 `INFORMATION_SCHEMA`의 실제 테이블·컬럼·제약

기존 문서의 실측 수치는 현재 DB 조회로 다시 확인하고, 확인 시점을 함께 적는다. 공식 API 설명과 실제 응답이 다를 때는 실제 적재 코드가 처리하는 형태를 본문 기준으로 삼고 차이를 주의사항에 남긴다.

## 6. 검증 기준

- 실제 H2 테이블 17개가 테이블 문서에 모두 등장한다.
- 각 테이블의 영속 컬럼이 컬럼 표에 한 번 이상 등장한다.
- PK·FK·유니크 제약이 실제 스키마와 일치한다.
- 자동 적재 API 네 개가 API 문서에 모두 등장한다.
- 원천 DTO와 LH 데이터셋의 모든 수신 필드가 응답 필드 표에 등장한다.
- 사용하지 않거나 저장하지 않는 필드는 그 이유가 기록된다.
- 요청 파라미터 이름·필수 여부·값의 출처가 실제 호출 코드와 일치한다.
- 문서 안에 `TODO`, `TBD`, 임시 자리표시자, 서로 충돌하는 수치가 없다.

## 7. 비범위

- 조회 API 설계와 구현
- DB 스키마 또는 적재 코드 변경
- 새 외부 원천 도입
- 기존 문서 삭제·대규모 재작성
- 현재 코드가 수신하지 않는 공식 API 전체 필드를 추측해 추가하는 일
