# 공고 주택형별 임대조건 저장 설계

## 목표

공고 화면에서 주택형별 공급 세대수와 임대조건을 함께 보여주면서도, 공고 당시 금액과 현재 LH 카탈로그 금액을 섞지 않는다.

## 원천 사실

- 마이홈 15108420은 공고 버전의 공급행별 `rentGtn`, `enty`, `surlus`, `mtRntchrg`를 준다. 정정공고는 새 `NoticeVersion`으로 저장되므로 과거 금액을 보존할 수 있다.
- LH 15056765는 특정 공고의 단지·주택형·전용면적·이번 회차 공급 세대수를 준다. `RFE`와 `LS_GMY`는 응답에 있어도 실제 응답에서는 `공고문 참조`인 사례가 있으므로 공고 주택형별 금액의 필수 원천으로 삼지 않는다.
- LH 15059475는 현재 카탈로그의 단지·공급유형·전용면적 행마다 `HSH_CNT`, `LS_GMY`, `RFE`를 준다. 이 값은 현재 기준 주택형별 전체 세대수·보증금·월임대료다.

## 저장 구조

1. `NOTICE_HOUSING`은 기존처럼 15108420 공급행 스냅샷과 공고행 임대조건을 보존한다.
2. `LH_LEASE_INFO`에 15059475의 `LS_GMY`, `RFE`를 추가해 원천값을 버리지 않는다. 유일하게 확인된 카탈로그 주택형에는 이 값을 `UnitType.baseRentTerms`에도 반영한다.
3. 이미 존재하는 `NOTICE_HOUSING_UNIT_TYPE_MATCH`를 공고 주택형 연결 read model로 확장한다. 새 중복 테이블을 만들지 않고, 한 행이 `NOTICE_HOUSING`과 15056765의 주택형 공급행을 연결한다.
   - 공고 주택형 식별·세대수: `type_name`, `exclusive_area`, `supplied_unit_count`, `total_unit_count`
   - 연결 근거: `lh_unit_supply_id`, 선택적 `unit_type_id`
   - 화면용 공고 조건: 부모 `NoticeHousing.rentTerms`를 동일 값으로 복사하되, 이는 주택형별로 독립 산출된 금액이 아니라 해당 공고 공급행의 공통 조건임을 문서와 컬럼명으로 명확히 한다.
   - 화면용 현재 조건: 매칭된 `UnitType.baseRentTerms` 또는 15059475 원천값을 별도 컬럼으로 보여준다.

## 매칭·안전 규칙

- `NoticeHousingUnitType`은 15056765 공급행과 공고버전/단지 경로가 유일하게 확인된 경우에만 만든다. 기존 매칭 상태가 `MATCHED`가 아니면 `unit_type_id`는 null로 남기고 원천 주택형 행은 보존한다.
- 15056765가 금액을 `공고문 참조`로 주면 숫자로 변환하거나 주택형별로 추정하지 않는다.
- 공고행의 금액을 자식에 복사해도 부모 원천행은 삭제하지 않는다. 두 값은 같은 원천값의 중복 보관이며, 현재 카탈로그 금액과는 별개다.

## 검증

- 15059475 JSON의 `LS_GMY`·`RFE`가 `LhLeaseInfo`와 `UnitType.baseRentTerms`에 저장된다.
- 15056765 공급행과 공고행이 연결되면 `NOTICE_HOUSING_UNIT_TYPE`이 생성되고 공급 세대수와 공고행 조건을 조회할 수 있다.
- 정정공고 버전마다 자식 행과 공고 조건이 분리되어 과거 금액이 현재 금액으로 덮이지 않는다.
- `공고문 참조`, 빈 값, 미매칭 주택형은 null/원문 보존으로 처리된다.
