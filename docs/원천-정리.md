# 원천 정리 — 무엇을 이을 수 있고 무엇을 못 잇나

건설임대만 다룬다는 전제에서, 다섯 원천이 각각 **무슨 알갱이로 무슨 키를 주는지**, 그래서 **어디끼리 이어지고 어디서 끊기는지** 정리한다. 개별 필드 사전은 [원천-API-데이터-사전.md](원천-API-데이터-사전.md), 모델이 왜 그 모양인지는 [도메인-설계.md](도메인-설계.md)에 있다.

이 문서의 수치는 전부 적재된 실제 DB를 센 것이다. **2026-08-16 전국 재적재 기준으로 단지 3,038행 · 주택형 10,024 · 공고 55 · 공급행 278**이다. 스키마 이력은 [테이블-설계-사전.md §8](테이블-설계-사전.md)에 있다.

그날 세 가지가 바뀌었다.

- 주택형 매칭에 공급면적 단계가 붙어 **공급행 주택형 확정이 198 → 227**, 면적 모호가 29 → **0**이 됐다(5장).
- **장기전세 제외가 데이터에 적용됐다** — 단지 248 · 주택형 1,146이 빠졌다(1장).

---

## 1. 경계 — 건설임대만

| | 담나 | 왜 |
| --- | :---: | --- |
| 건설임대 | **○** | 공공이 지은 단지. 이름·주소·PNU·주택형이 다 있다 |
| 매입임대 | ✕ | 민간주택을 한 채씩 사들인 것. "단지"가 없고 단지명 칸에 지역명이 온다 |
| 전세임대 | ✕ | 세입자가 직접 구해온 집. 대상 주택이 우리 쪽에 없다 |
| 분양 | ✕ | 빌려주는 게 아니다. 보증금·계약금·잔금의 뜻도 다르다 |

허용 공급유형은 영구·국민·행복주택·통합공공·5년·10년·50년임대 일곱이다. 이름으로 판정하지 않고 API별 코드 목록으로 거른다. 마이홈 공고는 요청 파라미터(`suplyTy`)부터 이 일곱만 돈다.

장기전세는 뺐다. 248단지 중 242가 SH공사이고 평균 135세대인데, 단지명이 "힐스테이트동작시그니처(동작하이팰리스지역주택조합)"처럼 민간 정비사업 단지에 몇십 세대씩 박힌 매입 물량이다. 245개가 `houseTyNm="아파트"`라 건설 흔적 검사로는 안 걸러지고, 원천에 건설·매입을 가르는 필드가 없어 유형 단위로 끊었다.

**2026-08-16에 데이터에도 적용했다.** 단지 248 · 주택형 1,146이 빠져 3,038 / 10,024가 됐다.

한 가지 주의할 게 있었다. **적재는 upsert와 reject만 하고 삭제를 하지 않는다.** 그래서 정책에 유형을 추가해도 이미 들어와 있는 행은 `/complexes`를 다시 돌려도 안 빠지고, 갱신이 멈출 뿐이다. SQL로 먼저 지우고 재적재해야 한다. 지우기 전에 FK 노출을 확인했는데 그 단지를 가리키는 공급행이 0건이라 깔끔했다. 재적재 후에도 장기전세가 0으로 유지된 게 정책이 재유입을 막는다는 확인이다.

실적재 결과 전국 256개 시군구에서 고유 단지 2,837개(단지·공급유형 3,038행)가 남고, 123,986건이 공급유형(매입·전세·장기전세 등)으로, 80건이 "라벨은 건설임대인데 준공일·주택유형 증거가 없음"으로 걸러졌다.

## 2. 원천 다섯 — 알갱이와 키

**알갱이(grain)**는 "원천 한 행이 무엇 하나인가"다. 이게 안 맞으면 조인이 성립하지 않는다.

| 원천 | 한 행이 무엇인가 | PNU | 주소 | 단지명 | 주택형 | 공급 세대수 |
| --- | --- | :---: | :---: | :---: | :---: | :---: |
| **15110581** 마이홈 단지정보 | 단지 × 공급유형 × 주택형 | ✅ | 도로명 | 마이홈식 | ✅ | 단지·유형 전체 |
| **15108420** 마이홈 모집공고 | 공고 × 공급행(단지) | ✅ | 도로명 | 마이홈식 | ✕ | 공고 전체 |
| **15057999** LH 공고상세 `dsSbd` | 공고 × 단지 | ✕ | 소재지 | **LH식** | 범위값만 | ✕ |
| **15056765** LH 공급정보 `dsList01` | 공고 × 단지 × **주택형** | ✕ | ✕ | **LH식** | ✅ | **이번 회차** |
| **15059475** LH 임대단지 카탈로그 `dsList` | 지역 × 공급유형 × 단지 × 전용면적 | ✕ | ✕ | **LH식** | 전용면적 | **전체** |

여기서 두 가지가 갈린다.

**PNU는 마이홈 계열에만 있다.** 카탈로그와 공고 양쪽에 있고, 마이홈 공고 공급행도 PNU를 보존한다. LH 계열(15057999, 15056765, 15059475)에는 PNU도 `hsmpSn`도 없다.

**주택형별 세대수는 두 의미로 나뉜다.** 15056765의 `NOW_HSH_CNT`는 이번 공고의 공급 수이고,
15059475의 `HSH_CNT`는 그 전용면적 주택형이 단지 전체에 몇 세대 있는지다. 마이홈 공고는
"이 단지에 총 몇 호"까지고, LH 공고상세는 전용면적을 `36.67~51.93` 같은 범위 문자열로만 준다.

## 3. 단지명이 두 체계다 — 이 문서의 핵심

마이홈과 LH가 같은 단지를 **다른 이름**으로 부른다. 주소·세대수로 같은 단지임이 확인된 85쌍을 비교한 결과다.

```
이름 일치   16건 (19%)
이름 불일치 69건 (81%)
```

불일치의 실제 모습:

| 카탈로그(마이홈) | LH |
| --- | --- |
| `하나로아파트` | `군산조촌부향` |
| `김해구산주공1단지아파트` | `김해구산` |
| `4단지` | `화성동탄2 A24블록 영구임대` |
| `율계마을` | `고창율계 고령자복지(영구임대) 주택` |
| `산북부향하나로1차` | `군산부향1차` |
| `평화주공4단지` | `전주평화4 영구임대주택` |

마이홈은 **동네에서 부르는 이름**, LH는 **사업지구명 + 블록 + 공급유형**이다. 명명 체계 자체가 다르다.

**그래서 정규화로 못 고친다.** 공백을 지우고 괄호를 떼고 접미어를 잘라도 `하나로아파트`가 `군산조촌부향`이 되지 않는다. 유사도 임계값을 낮추면 틀린 단지가 붙기 시작한다 — 매입임대 단지명이 지역명이라 이름 매칭이 위험하다는 것과 같은 종류의 함정이다.

**LH 단지명을 카탈로그 단지명과 직접 대조하는 매칭은 성립하지 않는다.**

## 4. 그래서 무엇이 이어지나

측정된 링크만 적는다.

| 잇는 것 | 키 | 실측 |
| --- | --- | --- |
| 공고 공급행 → 카탈로그 단지 | **PNU** | 97 / 111 확정. 미매칭 8, 후보 다수 6 |
| 공고 공급행 → LH 공고상세 | **주소 접두어** | 95 확정(주소+세대수 46, 주소만 49). 미매칭 23, 세대수 충돌 3 |
| LH 공고상세 ↔ LH 공급정보 | LH식 단지명, 같은 공고 안 | **290 / 290 (100%)** |
| LH 공급정보 → 카탈로그 단지 | 단지명 직접 대조 | **끊김 (19%)** |
| LH 임대단지 카탈로그 → 마이홈 `UnitType` | 지역·단지명·공급유형·`SUM_HSH_CNT` + 정확한 전용면적 | **1,487 / 6,710 확정** |

주소 칸을 "지번"이라고 부르던 자리를 고쳤다. `NoticeSupply.suppliedAddress`에 실제로 들어 있는 값은 마이홈 `fullAdres`에서 온 **도로명**이다(적재된 247건 중 도로명 245 · 지번 2). LH `dsSbd`의 `LGDN_ADR`을 그 값으로 접두어 비교하는 게 이 매칭이다.

마지막 두 줄이 이 문서의 결론이다. **같은 단지를 가리키는 이름이라도 누가 붙였느냐로 갈린다** — LH가 붙인 이름끼리는 290행이 전부 맞았고, LH 이름을 마이홈 이름과 맞추려 하면 19%로 떨어진다.

그림으로 보면 이렇다.

```
[마이홈 계열] ───── PNU ─────┐
                            ↓
  공고 공급행 ──────────> 카탈로그 단지 ──> 주택형(전용면적)
      │
      └── 주소 ──> LH 공고상세 ─ ? ─ LH 공급정보(주택형·공급세대수)
                   (LH식 단지명)     (LH식 단지명)

15059475는 공고 체인과 별개로 전국 카탈로그의 전용면적별 전체 세대수를 보강한다.
단지 ID·PNU·주소가 없어 이름만으로 연결하지 않고, 일치가 유일할 때만 `HSH_CNT`를
`UnitType.totalUnitCount`에 기록한다.
```

`?` 구간만 아직 안 재 봤고, 나머지는 다 실측했다.

## 5. 주택형은 어떻게 얻나

여기가 이번에 다시 잡은 부분이다. **두 질문을 분리해야 한다.**

### 질문 A — "이 공고는 어느 주택형을 몇 호 공급하나"

**15056765를 적재하면 그 자체가 답이다. 매칭이 필요 없다.**

15056765 응답은 `PAN_ID`(공고)로 조회하고, 한 행이 `단지명 + 주택형 + 전용면적 + 이번 회차 공급 세대수`다. `PAN_ID`는 마이홈 공고의 `detail_url`에 이미 박혀 있어 새로 알아낼 값이 없다. 즉 **공고 → 주택형은 원천이 직접 준다.**

```
Notice ──< NoticeSupply
           LH 단지명 · 주택형 · 전용면적 · 금회 공급호수
```

이 경로에는 카탈로그도, PNU도, 이름 매칭도 안 들어간다. 원천 사실 그대로다.

### 질문 B — "그 주택형이 카탈로그의 어느 `UnitType`인가"

평면도·기준임대료 같은 카탈로그 정보를 붙이려면 필요하다. 4단계 체인이고, **풀렸다.**

```
dsList01 ─LH단지명─> dsSbd ─지번주소─> 마이홈 공급행 ─PNU─> 단지 ─전용면적─> UnitType
          290/290        95건            97건
```

가운데 **마이홈 공급행을 거치는 게 우회처럼 보이지만 필연**이다. LH 계열에는 PNU가 없고 카탈로그에는 LH 이름이 없다. 주소와 PNU를 <b>둘 다</b> 가진 행은 마이홈 공고 공급행뿐이라, 그것만이 두 세계를 잇는 다리다. 그래서 공급행에 `supplied_pnu`와 `supplied_address` 두 칸을 남긴다 — 질문 A에는 안 쓰이고 질문 B에서만 쓰인다.

이 네 구간은 이제 별도 match 테이블이 아니라 적재 시점에 풀리고, 결과는 `notice_supply`의
`housing_complex_id`·`unit_type_id` 두 칸에만 남는다. 못 붙은 이유는 `unmatched_reason` 한 칸이다.

실제로 돌린 결과(v4 DB 공급행 278, 2026-08-16 재적재):

| 결과 | 행 |
| --- | ---: |
| 주택형 확정 | **227 (82%)** |
| 주소 구간에서 끊김 | 24 (9%) |
| LH 응답에 그 단지 주택형 행이 없음 | 12 (4%) |
| PNU 구간에서 끊김 | 11 (4%) |
| 15056765가 없는 공고 | 4 |
| **면적이 모호해서 못 고름** | **0** |

`15056765가 없는 공고` 4건은 대전·부산도시공사, 경상북도개발공사, 강원개발공사 것이다. 15056765는 LH 전용이라 이 기관들은 원래 못 받는다. 여기에 LH 통합공공임대 1건이 `UNSUPPORTED_LH_SUPPLEMENT_TYPE`으로 더 있는데, 통합공공임대가 어느 `SPL_INF_TP_CD`로 응답하는지 아직 실측하지 못해 비워 둔 자리다.

두 가지가 눈에 띈다. **LH 단지명 구간에서는 한 건도 안 끊겼다.** 그리고 **단지만 확정되면 주택형은 전부 확정된다** — 면적 모호가 0이다. 남은 손실은 전부 앞 단계(주소·PNU·LH 원천) 문제다.

면적 모호를 0으로 만든 건 세 번째 규칙이다. 자세한 건 [주택형-알갱이와-매칭.md](주택형-알갱이와-매칭.md) 4장에 있다.

### 질문 C — "카탈로그에서 이 전용면적 주택형은 원래 몇 세대인가"

15059475가 이 질문에 답한다. 한 `dsList` 행의 `HSH_CNT`가 `DDO_AR` 전용면적 주택형의
단지 전체 세대수이고, `SUM_HSH_CNT`는 단지·공급유형 전체 세대수다.

```
15059475 ──(이름 매칭)──> UnitType.totalUnitCount / baseRentTerms
   6,710행                    확정 1,481 / 10,024 (15%)
```

**15%에서 멈추는 건 이름 매칭 때문이다.** 이 원천에는 단지 ID·PNU·주소가 없어 LH식 단지명으로
붙일 수밖에 없는데, 마이홈 이름과는 19%만 맞는다(3장). 그리고 국민·행복·영구 계열만 다뤄서
50년·10년·5년임대 1,933개는 0건이다.

**이 칸은 LH 단지에만 찬다.** 비LH 3,376 주택형(SH 2,415 포함)은 0건이고 SH·GH 주택형별 세대수를
주는 원천은 포털에 없다. `null`이 정상값이고 `sum(total_unit_count)`를 전국 물량으로 읽으면 안 된다.

`ARA_NM`·`SBD_LGO_NM`·공급유형·`SUM_HSH_CNT`가 카탈로그 단지·공급유형 하나와 일치하고,
`DDO_AR`가 `UnitType.exclusiveArea`와 정확히 하나 일치해야 한다. 36.97과 36.9700처럼
소수 자릿수만 다른 값은 같은 값으로 보지만 ±0.05㎡ 근사 매칭은 하지 않는다.
같은 주택형을 여러 원천행이 가리키면 마지막 `HSH_CNT`가 앞 값을 덮어쓰지 못하도록 아무것도 반영하지 않는다.
원천행은 저장하지 않는다 — 한 번 호출이면 전부 받아서 재적재 비용이 거의 없다.

## 7. 남은 결정

1. **끊긴 51건을 더 붙일 것인가** — 주소(24)·PNU(11)·LH 원천(16) 구간 손실이다. 주소 정규화를 넓히면 더 붙지만 틀린 연결도 같이 는다. 지금 규칙은 의도적으로 좁다.
2. **여러 공급행이 같은 `UnitType`을 가리키는 걸 정상으로 볼 것인가** — 15056765는 `26A(청년)`/`26B(고령자)`처럼 공급대상까지 쪼개고 카탈로그는 `26` 하나다. 카탈로그를 더 쪼갤 문제가 아니라 **원천이 더 잘다**는 뜻이다. 붙이는 건 이제 다 붙는데(면적 모호 0), FK 가 1:N 이 된다는 사실은 그대로다. `unit_type_id` 로 세대수를 집계하면 안 되는 이유가 여기 있다([주택형-알갱이와-매칭.md](주택형-알갱이와-매칭.md) 5장).
3. **CSV 로 못 붙인 500쌍 중 127쌍을 세대수로 붙일 것인가** — `(시군구 + 공급유형 + 총세대수)`로 유일하게 특정된다. 주소가 잘려 있어서 못 붙은 단지라 그것 말고는 키가 없는데, 세대수로 붙이는 건 틀린 연결이 섞일 여지가 크다. 지금은 안 붙인다.
4. **`SPL_INF_TP_CD` 060/061은 아직 표본이 적다** — 54개 공고 전부 성공했고 그 안에 행복주택(063) 20건, 영구·국민임대(062) 33건이 들어 있어 실질 검증됐다. 50년(061)·10년(060)은 각 1건뿐이다.
5. **통합공공임대의 `SPL_INF_TP_CD`를 못 찾았다** — `LhSupplyInfoTypeResolver`가 이 유형만 비워 두고 있어 해당 공고는 주택형 단위로 못 쪼갠다. 카탈로그에는 20단지 108주택형이 있는데 공고 표본이 1건뿐이라 아직 실측하지 못했다.
